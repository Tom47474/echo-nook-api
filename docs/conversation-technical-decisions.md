# 对话功能技术难点与解决方案

更新时间：2026-11-25。本文对应 [开发路线图](conversation-roadmap.md)，记录已经实现的前后端方案、关键代码、验证和边界。路径中的 `echo-nook-web` 指同级前端仓库。代码行为发生变化时，以实际代码和测试为准，及时修订本页，不能把历史方案写成当前实现。

## 如何维护

每完成一个路线图任务（不必等整个阶段结束），在相应阶段追加或更新：问题与约束、前后端各自怎样实现、关键接口和数据流、竞态/失败处理、对应代码与测试、已知限制。同步更新本文日期和路线图状态。改变既有行为时明确写出“原方案 → 当前方案”，避免读者照旧方案操作。这里解释设计原因；[服务端架构](backend-architecture.md)记录当前接口和目录，[数据库指南](database.md)记录操作命令，前端细节另见 [前端架构](../../echo-nook-web/docs/frontend-architecture.md)。不要写入密钥、数据库密码或真实对话正文。

### 后续任务的写作标准

后续每一项技术难点都按本页 S3-1“乐观消息怎样与数据库正式消息对齐”的详细程度撰写，不能只用一句话概括“使用某技术解决某问题”。至少写清以下内容：

1. **问题从何而来。** 给出实际操作场景、触发条件及不处理会导致的具体错误，例如切换会话后旧 SSE 分片进入新会话。
2. **数据如何一步步流动。** 从用户操作或 HTTP 请求开始，按发生顺序写出前端 Hook、请求适配层、服务端路由、数据库/模型以及响应事件各自做了什么；必要时给出请求、SSE、消息状态或序号的简短示例。
3. **核心代码为什么这样写。** 定位到真实文件、函数或接口，解释 ID、状态、事务提交、行锁、取消、版本号等关键选择的目的；说明前端与服务端的职责边界。
4. **失败与并发怎样处理。** 至少覆盖该任务实际相关的错误、取消、乱序或重入场景，并说明页面显示与数据库最终状态；没有覆盖的情况应明确列为限制。
5. **怎样验证、还剩什么。** 记录有针对性的测试或手工验收及结果，注明当前实现与后续阶段的边界。历史实现改变时写明旧行为和新行为，不让已废弃方案冒充当前代码。

写作时用具体例子说明状态变化，例如“临时用户 ID → `message.started` 中的正式 UUID → 刷新后读取同一条数据库消息”；关键流程可以使用短代码块或时序图。每个结论须能从当前代码或测试核对，不猜测供应商行为，也不把计划中的能力写成已实现。

## 当前端到端流程（完成 S3-4 后）

```text
浏览器初始化 → 读取 URL 的 conversation 参数 → GET 会话列表和指定会话 → GET 指定会话最新 100 条消息
用户向上滚动/点击按钮 → GET 更早消息?before_sequence=游标 → 前插去重并补偿滚动位置
发送文本 → 没有会话则 POST 创建 → 本地先展示用户/助手占位
POST /api/v1/conversations/{id}/messages:stream，仅发送本次 message
服务端锁定会话 → 分配 sequence → 同一事务插入 user/completed 和 assistant/streaming
提交并释放锁 → 从数据库读取旧消息 → 组装完整回合 → 结束读事务
SSE message.started（正式 ID/sequence）→ 前端替换临时 ID
模型分片 → SSE message.delta → 前端追加正文，服务端周期性保存草稿
正常/失败/停止 → 服务端保存 completed/failed/cancelled → 前端呈现状态
```

浏览器调试注入的消息只存在内存中，不进入模型历史。旧的无会话 ID 流式接口仍存在，但当前前端使用带 ID 的持久化接口。

## 阶段零：环境隔离与调试工具（S0-1～S0-5）

### 难点：开发分支也需要调试球，而正式环境绝不能显示

Git 分支决定代码版本，不可靠地决定进程运行环境。调试组件保留在共享主线，前端 [page.tsx](../../echo-nook-web/src/app/page.tsx) 在服务端读取 `APP_ENV` 和 `ENABLE_CONVERSATION_DEBUG`：仅 `development` 或 `test` 且开关为 `true` 时把启用标志传入客户端。`production` 即使误设开关也不挂载调试入口。不能靠 URL 参数或浏览器存储开启。服务端 [config.py](../app/core/config.py) 用限定值校验 `APP_ENV`；测试服务器使用 `APP_ENV=test`，生产显式使用 `production`。`.env.example` 是无密钥模板，实际 `.env`/`.env.local` 是各机器的配置，不由 Git 分支自动切换。

具体判断发生在 Next.js 页面渲染时：`page.tsx` 计算 `debugEnabled = (APP_ENV 为 development/test) && (ENABLE_CONVERSATION_DEBUG 为 true)`，沿 `ChannelPage → ConversationPanel → useConversation` 传递。只有标志为真才渲染浮动球。假设开发者从 `master` 拉开发分支，代码仍包含调试工具；本地 `.env.local` 开启开关后能显示。假设正式部署也使用同一份代码，即使误写 `ENABLE_CONVERSATION_DEBUG=true`，由于 `APP_ENV=production`，标志仍为假。`NODE_ENV` 表示构建运行模式，测试服务器也可能运行 production 构建，不能用它代替业务环境。这里的门禁控制界面挂载，不构成阻止有权限修改代码的用户自行调用后端接口的安全边界。

### 难点：稳定复现 SSE 故障，不干扰真实接口

前端 [conversation-debug-panel.tsx](../../echo-nook-web/src/modules/conversation/components/conversation-debug-panel.tsx) 提供本地消息注入、批量消息、长文本、清空等操作；[debug-reply-provider.ts](../../echo-nook-web/src/modules/conversation/services/debug-reply-provider.ts) 包装真实流，模拟发送前阻止、部分内容后中断、缺少完成事件、慢速分片和服务商错误。故障由浏览器适配层制造，服务端没有公开故障注入端点。模拟断流只验证 UI 处理，不等于真实供应商一定立即停止计算或计费。停止操作仍通过真实请求取消路径验证。

Provider 包装层的调用次序是 `Hook → DebugReplyProvider → HttpReplyProvider → FastAPI`。例如“发送前阻止”在请求进入 HTTP Provider 之前抛出结构化网络错误，因此不会创建服务端消息；“慢速流”在每个事件前等待约 800ms，可观察思考状态和取消按钮；“部分内容后断流”在累计收到一定长度的 `delta` 后抛错，检查页面能否保留部分正文。选择的场景在一次发送开始时固定，途中更换下拉框不会改变已启动的请求。手动注入消息只修改 Hook 的本地消息数组，刷新后消失；真实发送的历史由服务端数据库提供，注入内容不会混入模型上下文。

### 验证和边界

阶段零检查了开发/测试启用与生产强制关闭构建，并通过服务端流关闭测试验证上游 Provider 会被 `aclose()`。生产部署仍须正确设置环境和跨域来源；环境门禁不代替未来的身份鉴权。

## 阶段一：对话链路稳定性（S1-1～S1-5）

### 难点：生成失败发生在收到部分正文之后

只显示一个“失败”会丢掉已经阅读的内容。前端 [use-current-conversation.ts](../../echo-nook-web/src/modules/conversation/hooks/use-current-conversation.ts) 在 `delta` 时累加正文；失败时保留正文并置 `failed`，将结构化错误交给 [message-item.tsx](../../echo-nook-web/src/modules/conversation/components/message-item.tsx) 展示。服务端 [service.py](../app/conversations/service.py) 将配置缺失、鉴权失败、模型不可用、限流、超时、不可达和一般异常编码成 `message.failed`，不在错误文案中回显上游密钥或响应正文。前端 [conversation-error.ts](../../echo-nook-web/src/modules/conversation/model/conversation-error.ts) 将配置、鉴权和模型不可用标为不可直接重试，其余可再次尝试。

以模型先输出“第一段”后超时为例：`HttpReplyProvider` 解析第一个 `message.delta`，Hook 找到当前助手消息并把文本追加到 `content`；服务端随后产生 `message.failed`，Provider 将 `code` 和安全的提示文案包装为 `ConversationRequestError`；Hook 的 `catch` 只改变该消息的 `status` 和 `error`，不清空 `content`。消息组件仍显示“第一段”，并在下方显示错误说明。服务端 S2-5 后也会把这段正文和 `failed/error_code` 落库，所以重新加载仍可看到残缺回答。若失败发生在第一个分片之前，正文为空，组件显示“未生成可展示的回复”。

错误码与恢复操作分开处理：401/403 映射鉴权失败，404 映射模型不可用，429 映射限流；超时、连接失败和其他上游异常分别归类。配置或权限问题通常需要修改服务端设置，直接重复发送不能解决；网络、限流、超时等可再试。UI 是否展示“再次提问”由错误的 `retryable` 属性决定，而服务端错误码始终可在持久化消息中保留。

### 难点：停止、断流与后续历史的语义

浏览器通过 `AbortController` 中止 `fetch`；[http-reply-provider.ts](../../echo-nook-web/src/modules/conversation/services/http-reply-provider.ts) 在消费者提前结束时取消响应读取器；服务端流生成器在 `finally` 关闭模型 Provider，真实适配器随之释放上游 HTTP 响应。单靠页面标成“已停止”不足以释放连接，因此前后端都处理关闭传播。模型供应商是否立即停止计费不由本项目保证。

实际停止路径依次是：用户点击停止 → Hook 对当前 `AbortController` 调用 `abort()` 并把本地 `streaming` 消息改为 `cancelled` → 浏览器终止流读取 → FastAPI 流生成器关闭 → 服务端在 `finally` 中 `aclose()` 模型流并尝试保存 `cancelled`。网络中断也会走资源关闭路径，但前端可能先显示本地网络错误；后续重新读取数据库消息时，以服务端实际终态为准。`reader.releaseLock()` 只释放 JavaScript 对读取器的占用，不能保证网络连接结束，因此提前退出时还调用 `reader.cancel()`。

在阶段一的纯内存实现中，前端按 `turnId` 保持完整问答；部分失败/取消的助手正文带内部“未完整生成”标记进入后续上下文，空回复只保留用户问题。接入数据库后，这项上下文选择移至服务端 [build_database_history()](../app/conversations/service.py)；浏览器不再上传 `history`。前端仍保留同步 `messagesRef`，使停止后立即发送不会读取 React 尚未提交的旧状态。

例如一个回合只有用户问题和半段已取消的回答，后续模型可以看到问题及半段回答，但半段回答附有系统注记，提示它不是完整结论；如果助手一个字都没有生成，就只带用户问题。按完整回合截取可避免上下文从孤立的助手回答开始。`messagesRef` 的作用是解决 React 批量状态更新：点击停止和立即发送可能发生在一次渲染提交之前，若新发送直接读取闭包里的 `messages`，会重新拿到尚标记为 `streaming` 的旧状态；同步 ref 在每次更新消息时先写入最新数组。

### 难点：重试语义随持久化而改变

S1-2 最初在内存里清空旧助手气泡并原地重新生成，不增加用户消息。S3-1 接入数据库后，服务端还没有覆盖旧回复的接口；继续原地改 UI 会导致刷新后旧回答重现。当前按钮改为“再次提问”，把原问题追加为新的持久化回合，保留旧记录。若今后要求真正原地重新生成，需要先设计服务端版本关系、历史选择和审计规则，不应仅在前端改气泡。

具体例子：旧回合在库中是 `user #4 / assistant #5`。点击当前按钮后，前端找到与 #5 同一 `turnId` 的原问题，再调用普通 `send`；服务端新建 `user #6 / assistant #7`。旧 #4/#5 不被改写，刷新后四条消息仍一致。阶段一内存版可以复用 #4/#5 的前端 ID，因为没有数据库；这个行为已经明确废弃。将来若产品要求“同一问题的多个候选回答”，需要确定原回答是否保留、哪条候选进入历史、如何标识版本，以及是否允许用户切换候选。

### 验证和边界

阶段一测试覆盖部分回答保留、结构化错误、主动停止和连接释放。当前流式消息的持久化终态由 S2-5 实现；断网时本地可先显示失败，数据库最终状态以服务端实际处理和后续重新加载为准。

## 阶段二：数据库与会话消息持久化（S2-1～S2-5）

### S2-1：异步连接、环境隔离与迁移

[Settings.active_database_url()](../app/core/config.py) 在 `APP_ENV=test` 时选 `TEST_DATABASE_URL`，其他环境选 `DATABASE_URL`；地址用 `SecretStr` 避免日志泄密。[DatabaseManager](../app/db/session.py) 验证 `postgresql+asyncpg`，测试环境额外要求库名以 `_test` 结尾；建立异步 Engine、Session 工厂，`pool_pre_ping` 检查失效连接，请求异常时回滚。FastAPI [lifespan](../app/main.py) 启动执行 `SELECT 1`，关闭释放连接池。Alembic 使用同一配置管理 schema；开发、测试库分别升级。这样连接错误在启动时暴露，测试不会意外写入开发库。

连接生命周期可以理解为“一个应用持有一个连接池，每次请求借一个 Session”：`create_app` 把配置保存在 `app.state`；lifespan 创建数据库管理器、执行 ping，然后把管理器交给依赖注入；路由通过 `get_db_session` 取得请求级 Session。写操作由路由显式 `commit()`，抛异常则上下文回滚；应用关闭统一 `dispose()`。`pool_pre_ping` 处理连接池里被 PostgreSQL 关闭的旧连接，不能替代启动时的 `SELECT 1`。测试库门禁核对的是 URL 中解析出的数据库名称，不在日志输出完整 URL。Alembic 迁移从应用配置取得地址，避免在迁移配置文件中重复保存密码；先升级数据库，再启动需要新表的服务代码。

### S2-2：模型约束和可扩展状态

[Conversation / Message](../app/conversations/models.py) 使用 UUIDv7。会话有标题、创建/更新时间和可空 `owner_id`；消息有角色、正文、`sequence`、状态、错误码和时间。数据库约束限制角色与状态、禁止负序号、保证 `(conversation_id, sequence)` 唯一；删除会话通过 `ON DELETE CASCADE` 清除消息。`owner_id` 只是未来身份阶段的预留字段，当前没有用户隔离效果。`0002_conversation_messages` 迁移建立表和约束，不能只定义 ORM 而不执行迁移。

`id` 解决跨请求定位具体会话/消息的问题，`sequence` 解决“同一会话中谁先谁后”的问题，两者用途不同。时间戳适合把最近活跃会话排到顶部，但两条消息可能具有相同数据库时间，不能单独依赖时间戳分页；因此会话内使用整数 `sequence` 和唯一约束。UUIDv7 可以在应用侧生成，且大体随时间递增。`status` 描述助手消息从占位到终态的生命周期：先 `streaming`，最后只能呈现 `completed`、`failed` 或 `cancelled`；`error_code` 为失败恢复提示提供机器可读依据。数据库检查约束和唯一约束是最后一道防线，即使 Python 并发逻辑出错，也不能悄悄写入重复序号。

### S2-3：管理接口和消息分页

[路由](../app/api/routes/conversations.py) 提供创建、列表、查消息、删除；[Repository](../app/conversations/repository.py) 集中 SQL 查询。会话按 `updated_at DESC, id DESC` 稳定排序，用 `offset/limit`；消息用 `before_sequence` 取比游标更早的一页，倒序多取一条判断 `has_more`，响应再反转为阅读正序。不存在的资源返回结构化 `conversation_not_found`；删除依赖数据库级联。当前列表最多请求 100 条，尚未实现列表继续分页；未完成 S5-1 前不能对外开放为多用户接口。

消息分页的例子：数据库有 `sequence=0…120`，客户端第一次请求 `limit=50`，查询按倒序拿 `120…70` 共 51 条；返回最新 50 条 `71…120`（给 UI 正序），因为多取到 #70，所以 `has_more=true`，`next_before_sequence=71`。下一次传 `before_sequence=71`，条件为 `<71`，便得到更早的 `21…70`，不重复 #71。会话列表另外使用 `updated_at` 排序，时间相同再用 ID 打破平局；二者分页方式不同。删除操作返回 204 后，消息由外键级联删除；删除或读取不存在的会话返回稳定的 404 错误码，便于前端区分资源消失和网络故障。

### S2-4：数据库成为模型历史的来源

新的 `POST /api/v1/conversations/{id}/messages:stream` 只接受 `message`，Schema 的 `extra="forbid"` 拒绝客户端传入 `history`。[start_turn()](../app/conversations/repository.py) 通过 `SELECT ... FOR UPDATE` 锁住会话行，在同一事务内计算下一顺序并创建用户/助手消息；提交后才调用慢模型，避免长期占锁。只查询本次用户消息之前且已进入终态的消息，包含空正文以便业务层判断最后一次助手尝试；[build_database_history()](../app/conversations/service.py) 按完整回合整理，最多 20 条、单条最多 4000 字符，并标记不完整的助手回答。历史查询后显式结束读事务，模型流期间不占用该数据库连接。旧无 ID 接口暂留作兼容，不能将它误认为持久化路径。

这里有两个独立的事务边界。第一段写事务锁定会话、取最大顺序、插入两条消息、更新会话活跃时间并提交；它结束后另一个请求才可分配后续顺序。第二段读取历史的 SELECT 会自动开启事务，路由组装完 `StreamMessageRequest` 后显式 `rollback()` 结束这个只读事务；慢速模型流随后才开始。若把数据库事务留到模型生成完毕，一个请求可能占连接几十秒，且阻塞同会话写入。历史查询使用 `sequence < 本次用户序号`，所以不会把当前问题或空的助手占位重复塞进历史；最后才将本次 `message` 附加到给模型的消息数组。

构造上下文时先从数据库扫描最近若干条可用消息，再按用户消息切成回合。一个回合中有用户问题和助手回答；若助手失败/停止且保存了部分正文，就在发给模型的正文末尾加“未完整生成”注记，页面展示的原文不变。最多选择 20 条，并保证取舍以回合为单位。这里按字符数和消息条数限制，尚未按模型 token 预算计算，属于后续 S4-1。

### S2-5：SSE 正文、终态与崩溃恢复

同一事务创建 `user/completed` 和空的 `assistant/streaming`，避免只落一半回合；会话行锁和唯一约束共同保护并发 `sequence`。SSE 先发 `message.started` 返回两条正式消息的 UUID 和顺序，再发 `message.delta`。 [stream_persisted_conversation()](../app/conversations/persistence.py) 累加正文：处理新分片时，新增至少 200 字符或距上次保存至少 1 秒才写草稿。每次通过独立短 Session 更新，慢模型流不长期占连接。完成或模型失败时，先保存完整/部分正文及 `completed`/`failed` 和错误码，再发送终态事件；仓储只更新仍为 `streaming` 的行，避免覆盖已结束消息。

并发例子：A、B 同时向同一会话发送。A 先锁住会话，看到最大序号 8，插入用户 #9 和助手 #10；B 必须等 A 提交，之后看到 10，再插入 #11/#12。两次模型生成可以并行，但序号分配不会交叉。数据库唯一约束额外防止错误实现产生重复 #9。

草稿保存例子：模型每次吐出几个字时，立即逐字写库会产生大量事务；当前包装器把 `delta` 累加到内存。某次新分片到来后，如果自上次保存新增至少 200 字符，或距上次保存至少 1 秒，就用新的短 Session 锁定助手行、保存当前完整草稿并提交。计时条件是在收到新分片时判断，没有后台定时写库。收到 `message.completed` 时无论是否达到阈值都保存完整正文和 `completed`，然后才把完成事件交给浏览器；`message.failed` 同样先保存部分正文、`failed` 和错误码。这样前端收到终态时，数据库已经完成对应写入。

客户端断开时，`finally` 关闭模型流，并用 `asyncio.shield` 尽量完成最后一次 `cancelled` 写入。进程强制退出无法执行 `finally`，下一次单进程启动由 [recover_interrupted_generations()](../app/conversations/persistence.py) 把遗留 `assistant/streaming` 改为 `failed`，错误码 `generation_interrupted`。最后一次检查点之后的少量正文可能丢失。若改多实例部署，需先引入生成任务租约/归属，避免一个新实例把其他实例正在生成的消息误判为失败。

取消与进程崩溃并不相同：正常断开时 Python 的生成器通常能运行 `finally`，保存已收到正文并把助手标记 `cancelled`；`asyncio.shield` 避免请求取消信号同时打断最后一次写库。强制杀进程时任何 `finally` 都不会执行，消息可能停留在 `streaming`，启动恢复才会将其改为 `failed/generation_interrupted`。恢复只修复状态，不可能重建尚未到达检查点的正文，也不会向已断开的浏览器补发 SSE。

### 验证和边界

阶段二的服务端测试覆盖迁移、唯一约束、级联删除、分页、并发顺序、历史来源、草稿检查点、完成、失败、停止及启动恢复。S2-5 完成时 28 项测试通过。身份鉴权、token 预算和多实例租约尚未实现。

## 阶段三：前端历史会话体验（历史实现）

本节记录 S3 当时的多会话实现和技术取舍。`conversation-list.tsx`、`use-conversation.ts`、`conversation-url.ts` 已在单窗口改造中删除；当前入口是 `use-current-conversation.ts`，现行产品行为以本文后面的“S5-1 当前方案”为准。

### S3-1：服务端会话与浏览器状态同步（已完成）

前端 [conversation-api.ts](../../echo-nook-web/src/modules/conversation/services/conversation-api.ts) 集中调用会话 REST API，把 `created_at`、`conversation_id`、`error_code` 等 DTO 映射为页面模型，并根据相邻消息还原 `turnId`。当时页面初始化读取会话列表，自动选择最近会话、查询最近 100 条；已删除的 `conversation-list.tsx` 曾提供新建、切换、删除，删除前确认。没有活动会话时，首次发送先创建会话。由于服务端列表按更新时间排序，生成结束会刷新列表，让活动会话回到顶部。

浏览器模型和数据库 JSON 有不同命名：服务端返回 `conversation_id/created_at/error_code`，组件使用 `conversationId/createdAt/error`。转换集中在 `conversation-api.ts`，因此消息气泡和列表不需要处理 HTTP 格式。恢复消息时，遇到用户消息把其正式 ID 设为当前 `turnId`，后续助手消息关联同一回合；失败消息依据 `error_code` 恢复提示。初始化的顺序是获取列表 → 选择服务端排序第一条 → 请求该会话最新 100 条 → 显示。列表为空时不预先创建空会话，首次发送才调用创建接口。

发送时已删除的 `use-conversation.ts` 会先放入临时用户和助手消息，避免等待网络时界面空白；这段乐观更新逻辑现由 [use-current-conversation.ts](../../echo-nook-web/src/modules/conversation/hooks/use-current-conversation.ts) 延续。前端 [HttpReplyProvider](../../echo-nook-web/src/modules/conversation/services/http-reply-provider.ts) 向带窗口 ID 的接口仅发送本次 `message`，逐个解析 SSE：网络分块可能截断事件，因此缓冲到空行才解帧。收到 `message.started` 后以正式 UUID 和 `sequence` 替换临时 ID；`delta` 追加正文，`completed` 标记结束，`failed` 转成结构化异常并保留已有正文。

#### 乐观消息怎样与数据库正式消息对齐

用户按发送后，Hook 先用 `crypto.randomUUID()` 造两条临时记录：用户消息立即出现在右侧，空助手消息显示“正在思考”。此时服务端可能尚未提交，两个 ID 只是浏览器渲染用的临时标识。服务端在同一事务中创建正式的用户/助手记录后，第一个 SSE 事件 `message.started` 携带 `user_message_id`、`assistant_message_id` 及两个 `sequence`。Hook 逐条匹配临时 ID：把用户消息换成正式用户 ID，把助手消息换成正式助手 ID，两条消息的 `turnId` 统一设为正式用户 ID，并记录序号；后续 `delta` 依据正式助手 ID 追加文本。这样刷新后从数据库加载的消息与刚刚显示的记录使用相同身份，不会出现“本地一条、数据库又一条”的重复。若请求在 `started` 前失败，本地临时消息会标失败；是否已经写库取决于服务端处理到哪一步，刷新后以数据库为准。

#### SSE 为什么需要缓冲和结构化事件

旧 Provider 只返回 `AsyncIterable<string>`，无法告诉 Hook 数据库正式 ID 或确切完成状态。现在事件包括 `started`、`delta`、`completed`，服务端的 `message.failed` 被转换为包含错误码的异常。网络一次 `reader.read()` 可能只拿到 `event: message.del`，下一次才拿到 `ta\ndata: ...\n\n`，也可能一次包含多个事件；Provider 把未读完的字节解码后保留在 `buffer`，只在空行界定完整 SSE 帧时解析 JSON。消费者提前退出时取消读取器，缺失完成事件且并非主动停止时抛 `stream_interrupted`，不会把半截回复误标成功。

切换会话时，Hook 先 `abort()` 旧 SSE，清空旧页面消息并加载目标会话。取消信号不能保证已经排队的 Promise 不执行，所以每个流还保存生成版本号，并在写入前核对当前活动会话 ID；两个条件都满足才更新页面。消息加载另有 `loadVersionRef`，避免先请求 A、后请求 B，却因 A 晚返回而显示错会话。列表刷新用 `listVersionRef` 防止旧列表响应覆盖刚创建或删除的项目。删除当前会话成功后选择剩余第一项；失败时显示错误并保留服务端返回前已有数据。

#### 三种异步竞态分别怎样处理

1. **旧生成流污染新会话。** A 正在生成，用户切换 B；Hook 先 `abort()`，并让旧生成版本失效。每个事件更新前同时检查“仍是本次版本”和“活动会话仍是 A”。即使 A 的网络分片或异常回调在 B 已加载后才到，也不能写 B 的消息数组。`finally` 清理控制器时也只清理自己创建的控制器。
2. **消息请求乱序。** 用户快速点击 A 再点击 B，B 的查询可能先返回。每次加载创建 `AbortController` 并增加 `loadVersionRef`；响应到达时核对版本及活动 ID，A 的晚到数据被丢弃。切换时先清空屏幕旧消息，避免 B 加载中继续展示 A。
3. **列表刷新覆盖新建/删除。** 生成完会刷新按 `updated_at` 排序的列表；若刷新请求尚未返回就创建或删除会话，旧列表响应可能把刚删的会话重新显示。新建/删除增加 `listVersionRef`，刷新结果只有版本仍一致时才提交到 React 状态。

删除使用服务端 `DELETE`，成功后从本地列表去掉该项；若它是活动会话，选择剩余第一项并加载消息。删除按钮先确认，因为数据库会级联删除全部消息。请求失败时保留列表并显示错误，不假装删除成功。

前端适配后的自动化测试覆盖 DTO 映射、SSE 跨块解析和正式 ID、部分失败、停止、切换隔离、删除后选择下一会话；S3-1 完成时前端 12 项测试、lint、production build 通过，服务端 28 项测试通过。S3-1 时刷新默认打开最近会话；S3-2 已增加 URL 指定恢复。超过 100 条消息的向上分页是 S3-3，阅读时的自动滚动优化是 S3-4。服务端还没有原地重新生成接口，因此当前“再次提问”会追加回合。

### S3-2：URL 保存会话 ID 并恢复消息（已完成）

#### 难点一：刷新后应该恢复链接指定的会话，而非最近会话

S3-1 只在 React 内存里保存活动 ID。用户先查看会话 A，再切到会话 B 并刷新，内存重置后又从按 `updated_at` 排序的列表选择第一项；如果另一会话近期更活跃，页面就不是刷新前的 B。S3-2 曾把活动 ID 放进 `/?conversation=<UUID>`。已删除的 `conversation-url.ts` 使用 `URL` 和 `URLSearchParams` 读写参数，保留页面原有其他查询参数及 hash。新建或点击列表切换时使用 `history.pushState`，给浏览器后退保留导航记录；首次没有参数而选择最近会话、或删除当前会话后选择替代会话时使用 `replaceState`，避免后退再次打开已删除地址。这里仅变更同一页面的查询参数，不触发整页重载。

一次直达请求的顺序是：浏览器打开 `/?conversation=B` → Hook 读取 URL → 加载会话列表 → 用服务端单会话接口验证 B 并取得标题 → 设置活动 ID 为 B → 请求 B 的最新 100 条消息 → 页面显示 B。此处增加 [GET 单会话接口](../app/api/routes/conversations.py)：如果 B 很久没使用，可能不在当前只读取的列表前 100 项；仅搜索列表会把存在的 B 错判为已删除。Repository 按主键读取，路由返回与创建/列表相同的会话 DTO；若列表里没有 B，Hook 将查询到的 B 加入可见列表，保证当前会话在导航栏中有对应项。消息正文仍从数据库读取，不从浏览器存储复制。

#### 难点二：URL、React 状态和浏览器前进/后退必须一致

仅调用 `pushState` 不会让 Hook 自动切换数据；反过来仅更新 `activeConversationId` 会让地址仍指向旧会话。列表点击时按“停止旧流 → 更新 URL → 设置活动 ID → 清空旧消息 → 加载目标消息”执行。浏览器后退/前进触发 `popstate`，Hook 重新读取地址并走恢复流程；恢复流程不再 push 新记录，否则后退会不断产生新历史项。原有的生成版本号和消息加载版本号继续拦截旧会话迟到的 SSE/查询响应。新建成功后才写入新 ID；创建失败保持原地址和原会话。删除当前会话成功后才改地址，选择剩余列表第一项；删除其他会话不更改当前 URL。

例如 A 正在流式回答，用户点击 B：A 的请求被取消，地址变为 B，随后 B 的消息从数据库加载。再按浏览器后退，`popstate` 读取 A，验证后恢复 A；即使旧 A 流的某个回调晚到，生成版本检查也不会让它混入当前重新加载的消息。这解决的是导航状态一致性，不保证浏览器断开时上游供应商立即停止计费。

#### 难点三：无效链接和网络故障不能混成同一种结果

服务端单会话接口在不存在时返回结构化 404；UUID 格式错误由 FastAPI 返回 422。前端 [conversationApi.get()](../../echo-nook-web/src/modules/conversation/services/conversation-api.ts) 将这两种情况解释为“目标不可用”，从当前列表回退最近会话、用 `replaceState` 改成真实 ID，并显示“链接中的会话不存在或 ID 无效”。如果没有任何可用会话，就清除该查询参数并展示空状态。回退是明确的 UI 行为，不能继续保留不存在的 ID 后又允许用户向它发送消息。

服务器不可达、500 等不属于“会话不存在”，适配层会抛出请求错误。首次直达加载失败时保留原链接和错误提示，便于刷新重试，不擅自改到别的会话；若浏览器后退时查询失败，则保留页面原来的活动会话，并把 URL 恢复为实际展示的 ID。消息接口加载失败时保持目标 ID、显示错误，避免把空列表误当成目标确实没有消息。未来可增加显式“重新加载”按钮；当前可刷新页面重新请求。

#### 验证和边界

前端测试当时验证了直达列表第一页之外的会话、失效链接回退、保留其他 URL 参数与 hash、浏览器后退、迟到 URL 查询、网络错误，以及 404 与 503 的不同处理；服务端测试验证按 ID 查询成功与结构化 404。完成 S3-2 时前端 18 项测试、lint、production build 和服务端 29 项测试通过。当时尚无身份归属校验；S5-1 后接口已按 `owner_id` 授权，单窗口改造又移除了 URL 会话导航。

### S3-3：按游标读取更早消息并保持阅读位置（已完成）

#### 难点一：新消息持续写入时，offset 分页容易重漏

假设会话已有 `sequence=0…120`，页面先显示最近 100 条。用户向上翻页时，助手可能还在生成、另一个请求也可能写入新回合；若按 `offset=100` 读取“第二页”，新记录会使排序整体位移，旧记录可能重复或漏掉。服务端 S2-3 已提供稳定的 `before_sequence` 游标：首次请求 `GET /messages?limit=100`，返回正序 `items`、`has_more`、`next_before_sequence`；下一次请求 `GET /messages?limit=50&before_sequence=<游标>`，数据库严格取 `sequence < 游标` 的记录。即使末尾新增更大的序号，较早页的边界不变。

前端 [conversation-api.ts](../../echo-nook-web/src/modules/conversation/services/conversation-api.ts) 完整保留分页元数据，不再只返回 `Message[]`；当前 [use-current-conversation.ts](../../echo-nook-web/src/modules/conversation/hooks/use-current-conversation.ts) 把下一游标存在 `cursorRef`，并用 `hasMore` 决定是否显示入口。例子：当前页面最早是 #71，服务端指示 `next_before_sequence=71`；再请求 `<71`，返回 #21…#70，不会重复 #71。只有服务端说有更多数据且游标非空时才发下一页。空页或没有更多记录时停止请求。

#### 难点二：拼接消息不只是数组相加

更早页从服务端按正序返回，Hook 把它放到现有消息前面。合并时先收集当前 UUID，再过滤新页中已显示的 ID，防止页面在请求交错或数据边界异常时出现重复气泡。回合 ID 还需要跨页修复：若旧页最后一条是用户 #50，而初始页第一条是助手 #51，初始页单独映射时不知道 #51 属于谁，只能暂用自己的 ID。加载旧页后重新按正序扫描合并后的消息，遇到用户就更新当前 `turnId`，随后助手继承它，于是 #51 正确关联 #50。消息的服务端 `id`、`sequence` 和正文保持不变。

同一时刻只能发一个更早页请求。Hook 用同步 `pagingRef` 在事件处理当下阻止按钮点击和顶部滚动连续触发两次相同游标；`loadingMore` 则让 UI 显示加载状态并禁用按钮。请求失败时保留已有消息和原游标，显示错误；用户再次点击会用相同游标重试，不会因为失败而跳过一页。切换、新建或删除当前会话时取消旧分页请求，并用 `loadVersionRef` 与活动会话 ID 双重核对响应归属。即使网络层忽略取消、旧页迟到，也不会插到新会话中。

#### 难点三：向上插入旧消息会把用户正在看的内容推走

用户停在最早一条已显示消息附近时，直接在数组前 `prepend` 50 条会增加列表总高度，原消息被推到视口下方。前端 [message-list.tsx](../../echo-nook-web/src/modules/conversation/components/message-list.tsx) 在请求前记录滚动容器的 `scrollHeight` 和 `scrollTop`；React 渲染新页后，`useLayoutEffect` 在浏览器绘制前计算 `新增高度 = 新 scrollHeight - 旧 scrollHeight`，再设置 `scrollTop = 旧 scrollTop + 新增高度`。例如旧高度 500、滚动位置 20，新增页让高度变成 800，就将滚动位置设为 320，原本可见的消息仍在原位置。该次更新不执行原有的“滚到底部”，否则补偿会立即失效。用户既可点击顶部按钮，也可滚动到顶部附近触发；两者走同一个加载函数。

这个补偿只针对插入更早页。流式新正文的自动跟随仍沿用旧逻辑，用户向上阅读时可能被新分片拉到底部；这是下一项 S3-4 的范围。布局中的图片等异步改变高度的内容尚未纳入二次补偿，当前对话主要是文本与 Markdown。

#### 验证和边界

前端测试验证游标参数及服务端游标映射、分页去重、无更多记录时不再请求、切换会话后丢弃迟到页，以及插入前后的滚动高度补偿；完成时 22 项测试、lint 和 production build 通过。服务端沿用阶段二已测试的游标接口，本次没有变更数据库或服务端接口代码。会话列表自身仍只读取最近 100 个会话，消息分页不会解决列表超过 100 项的导航问题；后续应另行规划列表分页或搜索。

### S3-4：阅读历史时暂停流式自动滚动（已完成）

#### 难点一：新分片到来不等于用户希望滚到底部

旧 [MessageList](../../echo-nook-web/src/modules/conversation/components/message-list.tsx) 每当 `messages` 改变就执行 `scrollIntoView`。模型每生成一小段 `message.delta`，Hook 都会更新助手正文，于是这个 effect 不断把列表拉到底部。假设用户正在上方阅读第 20 条历史，而助手在第 100 条继续生成，用户刚滚上去就会被下一片段拉回第 100 条，无法阅读历史。

当前消息列表以自己的滚动容器作为判断对象：每次滚动计算 `距底部 = scrollHeight - clientHeight - scrollTop`。距离不超过 80 像素时认为用户仍在跟随；超过阈值时认为用户正在阅读历史。阈值避免因文本排版、滚动惯性或小幅高度变化把“已经在底部”的用户误判为离开。是否跟随保存在同步 `followingRef` 中，滚动事件一发生就更新；`showJump` React 状态只控制“回到底部”按钮显示。新消息渲染后的 `useLayoutEffect` 只在 `followingRef.current` 为真时设置滚动位置。这样模型的 `delta` 改变正文，页面仍更新内容，但不会改变阅读者的 `scrollTop`。

#### 难点二：暂停后怎样恢复跟随

用户手动滚到距离底部 80 像素内时，滚动处理器将跟随标志恢复为真并隐藏按钮；之后每次新分片都会继续跟随到底部。用户也可以点击消息区水平居中、输入框上方的向下箭头。按钮仍通过 `aria-label="回到底部"` 提供可访问名称；点击后立即把跟随标志设为真并隐藏箭头，再调用 `scrollTo({ top: scrollHeight, behavior: "smooth" })` 平滑滚到最新内容。按钮位于滚动容器外层的绝对定位区域，不参与消息内容的 `scrollHeight`，因此出现按钮不会改变“离底部多远”的计算。

例如列表高 1000 像素、可视区高 400 像素、`scrollTop=550`，距底部 50 像素，继续跟随；用户向上滚到 `scrollTop=200`，距底部 400 像素，暂停。新分片使总高度增长到 1100 时，仍保持 `scrollTop=200`；点击箭头后向新底部平滑滚动，下一分片再次平滑跟随。

平滑动画会在中途产生 `scroll` 事件，此时滚动位置可能还远离底部。如果照常用 80 像素阈值判断，这些由程序发起的中间事件会把 `followingRef` 错误改为假，导致随后流式分片停止跟随、箭头提前重新出现。因此 `smoothFollowRef` 在调用平滑滚动前标记本次程序滚动；动画中尚未到达底部的事件不修改跟随意图，到达底部时清除标记。用户用鼠标滚轮或触摸开始主动滚动时，先清除该标记，让下一次滚动事件能正常暂停跟随。流式增量到来时将目标位置更新为新的 `scrollHeight`，浏览器继续向最新位置平滑滚动。

#### 难点三：与 S3-3 的向上分页、会话切换怎样协同

向上加载更早消息也会改变 `messages`，不能被当成“新回复需要跟随”。组件在分页请求前记下旧高度和位置；渲染后 `useLayoutEffect` **先**判断是否有本会话的前插快照，按 S3-3 的高度差即时补偿 `scrollTop`，并把跟随标志设为假，然后直接返回，不执行滚到底部。这里不做平滑动画，因为补偿的目的就是让原消息在同一屏幕位置不动。发生会话切换时，组件清除旧会话的前插快照、将跟随标志重置为真并隐藏按钮；目标会话的历史加载完成后即时展示最新消息，避免打开长会话时从顶部播放长距离动画。旧会话的分页响应仍由 Hook 的版本校验隔离，不会改变目标会话。

若加载更早页失败，已有消息和滚动位置不变，用户可重试。当前主要处理同步渲染的文字与 Markdown；未来若气泡包含异步加载的图片或媒体，其加载完成后会额外改变高度，可能需要 `ResizeObserver` 对阅读锚点做二次补偿。服务端 `message.delta`、分页接口和数据库结构在 S3-4 均无需改动。

#### 验证和边界

前端组件测试验证用户离开底部后收到新消息仍保持 `scrollTop`、箭头居中且有可访问名称、点击与流式跟随传入 `behavior: "smooth"`、动画中间事件不误停跟随、用户滚轮可以打断、接近底部阈值内继续跟随、切换会话重置跟随，以及既有的向上分页位置补偿。调整后前端 25 项测试、ESLint 和 production build 通过。阶段三至此完成；下一项是 S4-1 按 token 预算选择服务端模型上下文。

## S4-1：按估算 token 预算选择模型上下文（已完成）

### 难点一：条数和字符数不能代表模型实际容量

原先 [build_database_history()](../app/conversations/service.py) 只保留最近 20 条、单条最多 4000 字符。相同字符数的中文、英文、符号和代码在不同模型中会得到不同的 token 数；此外模型还会收到系统提示词、本次问题和每条消息的角色包装。只统计数据库历史，即使历史没有超限，完整请求仍可能占满窗口，让模型没有回答空间。

[Settings](../app/core/config.py) 现在配置 `LLM_CONTEXT_WINDOW_TOKENS`、`LLM_MAX_OUTPUT_TOKENS` 和 `LLM_TOKEN_SAFETY_MARGIN`，默认分别为 32768、4096 和 1024；启动时检查输出预留与安全余量之和必须小于窗口。窗口采用保守默认值，换模型时应按供应商公布的实际限制修改。服务端计算 `输入预算 = 窗口 - 输出预留 - 安全余量`。例如默认输入预算为 27648；这不是允许历史单独使用 27648，还必须先扣系统提示词与本次问题。

### 难点二：请求发出前没有供应商的实际用量

[estimate_message_tokens()](../app/conversations/service.py) 用 UTF-8 字节数加每条消息 16 token 的包装余量估算。这样中文通常会比按“一个字符一个 token”多占预算，能给未知分词器留空间；但字节数和固定余量不是供应商的精确分词结果，也不能保证对每种模型和特殊输入严格上界。这里不把估算结果记录为实际用量。真正的 `usage` 要等上游响应，属于 S4-4。当前模型请求通过 [OpenAICompatibleProvider](../app/llm/openai_compatible.py) 显式设置 `max_tokens`，使请求的输出上限与预算预留一致；推理模型的思考过程也可能消耗输出额度。

### 难点三：裁剪历史时不能丢掉当前问题或拆开回合

路由 [stream_conversation_message()](../app/api/routes/conversations.py) 先计算预算并检查 `系统提示 + 本次问题`。如果这两项已超预算，立即返回 HTTP 422、`input_budget_exceeded`，不执行 `start_turn()`，所以数据库不会留下一个永远无法生成的用户消息和助手占位消息。接口原有的单条 4000 字符验证仍有效；4000 字符内的高字节内容也可能触发预算错误。

通过检查后才原子创建回合、提交、读取历史。`build_database_history()` 先沿用现有逻辑将数据库消息组装成完整问答和中断注记，再从最近回合往前计算每个回合的估算 token，只有整个回合与现有 20 条上限都放得下才纳入。第一个放不下的旧回合出现后停止，不跳过它去挑更早的碎片；近期上下文因此保持连续。分页、会话归属和前端请求格式均未改变。历史读取后仍结束只读事务，再调用模型。

### 验证和剩余边界

测试验证预算只纳入最近完整回合、当前问题超预算会失败、HTTP 422 时数据库不新增消息，以及方舟请求携带与配置一致的 `max_tokens`；服务端全部 32 项测试通过。模型真实分词与供应商窗口约束仍可能和本地估算不同；若上游拒绝超限请求，后续需要根据实际错误类型细分响应和调校余量。S4-2 将进一步处理失败、取消和重新生成的问答关系；S4-4 才记录实际用量并据此校准估算。

## S4-2：在预算内保留合理问答关系（已完成）

### 难点一：空的最后一次失败不能让旧回答“复活”

历史表按 `sequence` 记录消息。设同一问题之后有 `assistant #5/completed/旧回答`，后来一次尝试留下 `assistant #6/failed/空正文`。旧查询先用 `content != ""` 过滤，会把 #6 从业务层视野中删除；组装历史时便误以为 #5 是最后一次结果。现在 [load_model_history()](../app/conversations/repository.py) 读取当前问题之前的终态消息，包括空正文。历史组装函数以同一用户消息之后最后一条终态助手记录为准：若它是空的失败/取消，模型只看到用户问题，不会再看到旧答案；若它有部分正文，就追加“未完整生成”内部注记。页面和数据库保存的正文不修改。

### 难点二：孤立消息和生成中占位不能进入历史

[build_database_history()](../app/conversations/service.py) 从时间正序扫描：只有已完成、非空的用户消息能开一个回合；没有前置用户消息的助手记录丢弃；`pending/streaming` 助手不覆盖最后一个终态结果。数据库查询仍限制在当前用户消息的 `sequence` 之前，并只取终态记录，防止把这次刚创建的空占位放入模型请求。函数在业务层重复检查状态，是为了直接调用或测试传入混合记录时仍保持相同规则。

完成、失败和取消的历史助手各有不同处理：完成的非空正文作为普通回答；失败/取消的非空正文后附内部中断注记，使模型知道它不是可靠结论；空正文不产生助手消息，对应用户问题仍可进入历史。按整个回合计算 S4-1 的 token 预算和 20 条上限，不能把用户问题与它的助手回答拆开。若最近一个回合已放不进预算，就停止向前选取，避免上下文出现更旧却缺失近因的片段。

### 难点三：“再次提问”与真正的重新生成没有相同的数据身份

当前前端按钮通过普通发送接口再次提交原问题。服务端会创建新的 `user/assistant` 对，旧回合仍在数据库；即使两条用户正文完全相同，也可能是用户有意重复提问，因此不能靠文本相等把它们合并。上下文会按顺序保留两回合，再由预算裁剪。将来若提供原地重新生成，需要显式的回合/候选回答关系和接口约定，决定哪些候选进入上下文；本阶段不伪造该关系。

### 验证和边界

服务端 36 项测试通过，覆盖孤立助手、最后一次空失败、取消的部分正文、相同问题的独立再次提问、生成中助手不覆盖终态，以及数据库查询确实保留空终态。当前模型历史查询最多扫描最近 100 条；如果窗口边界落在一个回合中间，孤立助手会被排除。长对话跨越这个扫描范围后的摘要与近期原文组合属于 S4-3。

## S4-3：长对话摘要与近期原文共同构造上下文（已完成）

### 难点一：只裁剪近期回合会永久丢失较早信息

S4-1 按预算选最近的完整回合；对长会话而言，较早的用户偏好、约定和未解决问题会被排除。S4-3 通过迁移 [0003_conversation_summary.py](../alembic/versions/0003_conversation_summary.py) 在 `conversations` 表保存 `summary` 以及 `summary_through_sequence`。后者是摘要覆盖的最后一条消息序号；它使服务端能够准确区分“已压缩旧消息”和“仍需原文的近期消息”，避免同一段对话以摘要和原文重复进入模型。

新请求先按原有事务创建用户/助手回合，再读取当前用户消息之前的终态历史。路由在 `rollback()` 前将 ORM 消息所需字段复制成独立快照，因为回滚会使 ORM 实例过期；若在释放数据库事务后访问原 ORM 属性，异步环境会尝试隐式 I/O 并失败。模型调用期间不持有前一段读事务。

### 难点二：摘要更新要有明确来源和边界

[summary_source()](../app/conversations/summary.py) 从上次覆盖序号之后的消息开始计数，保留最近 10 个用户发起的回合原文。只有旧回合超过这个数量才更新摘要；每次最多取最早的 3 个旧回合，在下一条用户消息之前截断，所以不会只压缩半个回合或把当前问题放入摘要。摘要输入先通过 S4-2 的 `build_database_history()` 转为有效问答，失败/取消的部分正文仍带内部中断注记；摘要提示要求模型保留偏好、已确认事实、未解决问题和结论，并避免把中断回答写成确定事实。摘要长度上限 2000 字，生成输入上限 4000 字。现有摘要与本次旧回合一起送给模型，生成新的滚动摘要。

例如已有 13 个旧回合，第一次请求会摘要前 3 个，保存覆盖到第 3 个回合末尾的 `sequence`，最近 10 个回合仍用原文。随后新对话继续增加时，超过 10 个的最早回合会逐步并入摘要。当前“再次提问”本身是独立的新回合，按实际 `sequence` 参与近期保留与旧段摘要。

### 难点三：摘要和主回复是两次不同的模型调用

[refresh_summary()](../app/conversations/summary.py) 只在 `openai_compatible` 模式触发；演示模式不调用演示 Provider 编造摘要。先调用模型生成摘要并及时关闭流，再用短事务更新会话。更新条件要求数据库中的 `summary_through_sequence` 等于本次开始时读到的边界；若并发请求已推进摘要，迟到请求不能覆盖它，而是读取较新版本。摘要不作为页面消息，也不暴露在 SSE 中。主回复构造时过滤已覆盖的原文，将摘要附在系统提示词中，再按 S4-1 的输入预算选择余下的近期原文。摘要也占用输入预算，若本次问题与摘要合计超预算，则不用摘要并回退到原文。

摘要模型报错、返回空结果或超过长度上限时，沿用已读到的持久化摘要和边界；摘要存储过程异常时，路由退回原始历史并按既有预算裁剪，不阻断主回复。调用摘要模型可能增加一次费用和主回复首字延迟。摘要是模型生成内容，可能遗漏细节，不能替代数据库原文；数据库中的全部消息仍保留供页面分页查看。当前旧会话首次摘要前会读取其全部终态历史，超长旧会话的读取量以后还需优化。

### 验证和运行步骤

测试覆盖摘要触发边界、覆盖序号持久化、生成失败保持旧摘要，以及真实路由将摘要作为系统背景信息、将近期原文交给主模型。服务端 39 项测试通过；本地开发库和测试库均执行 `alembic upgrade head` 到 `0003_conversation_summary`，两个环境的 `alembic check` 均无差异。其他环境须在运行新代码前迁移；后续 S4-4 再记录摘要调用和主回复调用各自的模型、耗时与真实用量。

## S4-4：记录模型调用信息与真实用量（已完成）

### 难点一：流式正文和最终用量不在同一个事件中

主回复和摘要都通过方舟 Chat Completions 流式接口生成。普通片段的 `choices[0].delta.content` 提供可展示正文；用量可能只在流结束前的额外片段中出现，且这个片段的 `choices=[]`。旧 [OpenAICompatibleProvider](../app/llm/openai_compatible.py) 在 `choices` 为空时直接跳过，因而即使供应商提供 `usage` 也无法记录。适配器现在显式发送 `stream_options.include_usage=true`，先读取每个事件里的模型名，只把尾块或带结束原因的终块中非空的 `usage.prompt_tokens/completion_tokens/total_tokens` 视为最终用量；中间片段的累计值不能冒充整次调用总量。随后从选择项中读取非空 `finish_reason` 和正文。用量尾块不变成前端 `message.delta`。解析只接受非负整数；字段缺失时保持 `None`，不把 S4-1 的字节估算写成真实 token。

### 难点二：两次模型调用必须分别归因

长会话可能先调用模型生成摘要，再调用模型生成最终回答。两次调用的提示词、耗时与 token 用量不同，不能合并成一次，也不能把摘要用量算到主回复上。迁移 [0004_model_calls.py](../alembic/versions/0004_model_calls.py) 增加 `model_calls` 表，每行保存会话 ID、可选的助手消息 ID、`purpose=summary|reply`、服务端结束状态、实际模型名、耗时、可取得的用量和供应商 `finish_reason`。没有提示词、回复正文或 API Key 字段；删除会话时外键级联清理这些记录。

适配器在真实请求开始时创建 [LLMCallMetrics](../app/llm/metrics.py)，用单调时钟测量直到上游流关闭的时间；异常或取消也会在 `finally` 写入已测得的毫秒数。摘要流结束后，[refresh_summary()](../app/conversations/summary.py) 写入一条 `summary` 记录；主回复由 [stream_persisted_conversation()](../app/conversations/persistence.py) 在消息终态确定、模型流关闭后写入 `reply` 记录。调用记录使用独立短事务，不延长模型流期间的数据库事务。演示 Provider 没有真实模型调用信息，因此不创建 `model_calls` 行。

### 难点三：失败、主动停止和缺失尾块不能伪造数据

服务端的 `status` 由实际链路决定：正常结束是 `completed`，供应商或生成错误是 `failed`，用户停止或连接关闭是 `cancelled`；这与供应商的 `finish_reason` 是两个不同字段。供应商可能在中途断流、超时或用户取消时没有发出用量尾块，也可能只提供部分字段；这时所有未得到的 token 值及 `finish_reason` 保持数据库 `NULL`。即使已收到部分正文，也不从文字长度倒推出真实用量。摘要失败时依旧按 S4-3 的策略回退到已保存摘要或近期原文；调用记录写入出错不能改变已经保存的消息终态或向前端发送的 SSE 结果。

例如一次长会话触发摘要，模型先用 30 个输入 token、10 个输出 token 生成摘要，再用另一份上下文生成回答；数据库会有两行，分别对应 `summary` 与 `reply`。若主回复在读到用量尾块前被停止，主回复行可为 `cancelled`，已知模型和耗时仍可保留，用量保持 `NULL`。不能把摘要行的 40 token 填入主回复行，也不能把估算预算当作它的用量。

### 验证和运行边界

测试覆盖 `choices=[]` 用量尾块、`finish_reason` 和实际模型名、缺失用量保留空值、摘要与主回复两条记录，以及失败和取消调用的已知字段与未知字段。服务端 42 项测试通过；本地开发库与测试库均升级到 `0004_model_calls`，两个环境的 `alembic check` 均无差异。可用 [数据库指南](database.md) 中的只读 SQL 在 DBeaver 查看最近调用。当前不提供面向前端的用量查询接口；阶段五的身份归属完成前，不应开放按会话查看内部调用记录的公共接口。

### 补充修复：终态 SSE 不能先于调用记录提交

浏览器的 [HttpReplyProvider](../../echo-nook-web/src/modules/conversation/services/http-reply-provider.ts) 读到 `message.completed` 后结束循环，并对尚未自然结束的响应体执行 `reader.cancel()`。旧服务端先把 `message.completed` 交给浏览器，只在异步生成器 `finally` 中调用 `record_model_call()`；客户端取消可能使 ASGI 流任务在数据库提交前终止。于是助手消息已经是 `completed`，页面也得到完整回答，但同一 `assistant_message_id` 没有 `model_calls`。调用记录异常又被 `except Exception: pass` 静默忽略，界面和服务日志都看不到原因。真实开发库曾出现连续两条完成消息缺少调用记录，证明这不是 DBeaver 缓存问题。

修复后的 [stream_persisted_conversation()](../app/conversations/persistence.py) 在识别 `message.completed` 或 `message.failed` 时，先用短事务保存助手终态，再通过取消安全任务提交 `model_calls`，成功后才 `yield` 终态 SSE。此时 Provider 已经结束或抛出异常，`last_call_metrics` 中的模型、耗时、结束原因和可取得 usage 已经稳定。即使浏览器在下一微秒取消响应体，关键调用记录也已经提交。记录写入失败仍不应把完整聊天改成失败，但现在使用不含正文、Cookie 和密钥的资源 ID 日志代替静默吞错。

主动停止没有 completed/failed 事件，不能使用同一前置时机。最终清理把 `source.aclose()`、助手 `cancelled` 状态和调用记录放入一个独立任务，并以 `asyncio.shield()` 防止请求取消连带中断；等待清理完成后才把 `CancelledError` 交还给 ASGI。一次流用 `call_record_attempted` 保证最多尝试写一条回复记录，正常终态进入 `finally` 时不会重复插入。新增测试在读取 completed 后、尚未关闭生成器时立即查询数据库，并直接取消正在等待后续片段的消费任务，分别验证完成 usage 已提交和取消调用仍留记录；另用模拟数据库异常验证记录失败会写日志，但助手消息和终态 SSE 仍保持 completed。

## S5-1 初版身份方案（历史记录，已被单窗口方案替代）

`0005_identity` 首次加入游客、账号、Cookie 会话、会话归属校验和调用时用量归属。当时短暂实现过“用户确认后把游客会话导入账号”，并为多会话页面返回 `importable_count`。随后产品确定游客与账号必须保留各自独立的消息，因此 `/identity/import`、`importable_count` 和前端导入提示已经删除。实施记录仍保留在 Git 历史和路线图中，不能再作为当前接口说明。

当前仍沿用的安全基础包括：浏览器只持有高熵随机 Cookie，数据库只保存 SHA-256 摘要；账号密码保存独立盐的 scrypt 哈希；Cookie 为 `HttpOnly`、`SameSite=Lax`，HTTPS 或正式环境启用 `Secure`；写请求校验 Origin；所有窗口和消息 SQL 都按服务端解析出的 `owner_id` 过滤，客户端不能提交可信身份 ID。完整现行流程见下一节。

## S5-1 当前方案：单窗口与游客/账号独立消息（2026-11-25）

### 难点一：只保留一个窗口，同时不能丢弃旧消息

旧版一个身份可以拥有多个 `conversations`，消息按 `(conversation_id, sequence)` 唯一。如果仅隐藏前端列表而仍按“最近会话”读取，其他会话会成为不可访问的暗数据；如果直接给 `owner_id` 加唯一约束，已有多会话的数据库迁移会失败。[0006_single_window.py](../alembic/versions/0006_single_window.py) 在事务中逐个处理已有身份：按会话创建时间确定合并顺序，选最后一个会话为当前窗口，读取全部消息并先把序号暂时改为互不冲突的负数，再迁入目标窗口并重新分配从 0 开始的正序号。模型调用记录改指向目标容器，旧容器在消息迁完后删除；多个原摘要无法安全拼接，因此清空摘要覆盖边界，下次模型调用从合并后的原文重新摘要。迁移最后创建 `is_current=true` 条件下对 `owner_id` 唯一的索引。没有可信归属的旧 `NULL` 会话不分给任意游客，仍走开发环境显式认领流程。

页面调用 `GET /api/v1/conversations/current`。[ConversationRepository.current()](../app/conversations/repository.py) 先锁身份行，再查询或新建唯一窗口；两个同时到达的首次请求不会创建两个窗口。旧多会话接口暂保留给旧版客户端与历史测试，新界面不再调用。前端移除历史会话列表、切换 Hook 和 `?conversation=` URL 逻辑，只使用 [use-current-conversation.ts](../../echo-nook-web/src/modules/conversation/hooks/use-current-conversation.ts) 加载唯一窗口。消息的 UUID、流式 SSE 对齐、向上分页和滚动体验继续保留，因为“没有历史会话列表”不等于“刷新后丢失同一窗口的旧消息”。开发库的旧无归属会话在人工确认目标身份后，由 `claim_legacy.py` 并入该身份当前窗口，不会因认领后仍是旧容器而继续隐藏。

### 难点二：身份切换时防止游客内容混进账号窗口

游客凭证与账号凭证一直独立。注册或登录只替换活跃 Cookie，不删除游客 Cookie，也不修改游客消息的 `owner_id`。账号退出时恢复仍有效的游客 Cookie；如果它已经过期，才建立新游客身份。[identity.py](../app/api/routes/identity.py) 删除了导入接口及 `importable_count` 响应字段，前端也不再显示导入提示。页头由 `ChannelPage` 持有当前身份，并把它交给右上角的 `IdentityControls`；游客只见“登录/注册”，账号只见默认头像，点击后显示用户名和退出。对话组件以 `identity.id` 作为 React key：身份变化时旧 Hook 卸载，关闭读取与 SSE 请求、丢弃内存消息；新 Hook 再从服务端读取新身份窗口。这样账号和游客即使在同一浏览器，也不会短暂显示对方消息。跨浏览器登录账号可恢复账号窗口；游客窗口仍只随原浏览器的有效凭证恢复。

### 难点三：清空消息与在途模型流并发

`DELETE /api/v1/conversations/current/messages` 由 Cookie 确定当前身份，前端确认后先取消本机 SSE，再调用接口。服务端锁住当前窗口行，在同一事务里删除其消息、重置摘要和覆盖序号，并递增 `content_epoch`；其他身份的窗口完全不受影响。新回合创建也锁此行，因此清空与开始发送有确定顺序。已在生成的流可能在清空后才完成，草稿写入以消息 ID 为条件，消息已删除时不会重新插入。摘要生成更慢：它先读取旧的 `content_epoch`，最终更新时同时要求版本仍相同；清空递增版本后，迟到的旧摘要无法重新写进窗口。前端若清空请求失败，会重新读取服务器消息，避免只在页面上清空而数据库仍有内容。

`model_calls` 是服务端成本与用量记录，清空不删除它们，也不改变调用当时保存的 `usage_owner_id/kind`。这与删除旧容器时的级联规则不同：当前窗口保留，清除的是 `messages` 与上下文摘要。界面仍不展示 token 用量。测试覆盖单窗口重复读取、游客/账号切换、清空隔离和调用记录留存；前端验证页头身份交互、当前窗口加载、清空失败恢复、REST 与 SSE。正式部署还需按 S5-4 验证多实例同时清空与流式生成、同站 HTTPS Cookie。

## S5-2：用户额度与调用限制（已撤销）

### 为什么撤销

S5-2 曾短暂实现游客/账号每日回复次数、每分钟发送次数、同身份和进程全局并发、登录失败窗口，以及配套的 429 前端错误。单窗口产品允许用户在生成过程中停止、修改问题并立即重新发送；低频分钟限制会把这些正常操作也当成异常请求。当前产品又明确为游客和登录账号均免费使用，不需要用户级次数或 Token 额度，因此继续保留这些拒绝规则只会增加误拦截和维护成本。

撤销采用前向 Git revert，而不是重置或改写 S5-1：服务端删除应用级限额器、额度配置、登录保护、并发租约、旧接口 410 和相关测试；前端删除四种额度错误码及专用测试。开发库和测试库在迁移文件仍存在时先从 `0007_s5_limits` 安全降级到 `0006_single_window`，再撤销迁移代码，避免数据库保留代码中不存在的版本号。

### 仍然保留什么

S4-4 的 `model_calls` 和供应商 usage 继续保留，S5-1 的 `usage_owner_id/usage_owner_kind` 调用时快照也继续保留；它们用于回答“哪个身份、哪种用途、哪个模型产生了多少可取得的 Token 和耗时”，但不再参与请求准入。清空消息、登录或退出仍不会改写历史调用记录，页面仍不显示 Token。

输入预算、单条消息长度、会话归属校验、SSE 主动关闭和 Provider 自带的 HTTP 连接/读取超时也不属于用户额度，继续按原阶段实现工作。前端保留供应商鉴权、模型不存在、供应商限流、网络错误和流中断等既有错误处理；只撤销 S5-2 新增的应用额度错误。

### 当前边界和后续

当前没有登录失败限流、用户分钟频率、单身份在途限制、应用全局并发或每日 Token/次数额度。用户可以在停止后立即重新发送，直接 API 调用也不会因应用额度得到 429。免费策略不等于供应商没有成本或硬限制：上游仍可能返回 429，usage 仍应由后续 S5-3 结构化日志观察。如果将来真实成本或滥用成为问题，需要基于当时的产品规则重新规划全局成本保护或 Token 预占结算，不能直接恢复已撤销的低频次数方案。
