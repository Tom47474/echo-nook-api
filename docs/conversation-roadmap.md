# 对话功能开发规划与进度

更新时间：2026-11-23

本文记录 EchoNook 前后端对话功能的后续实施顺序、验收要求和进度。当前仅建立规划，以下任务均未开始；不代表相关功能已经实现。

## 当前基础

- 前端通过 `fetch` 消费服务端 SSE，展示流式回复，支持停止和清空当前对话。
- 服务端通过统一模型接口支持演示回复和 OpenAI 兼容模型调用。
- 历史由客户端传入，最多 20 条；尚无数据库、持久化会话及历史恢复。
- 生成失败时前端删除本次助手消息；取消的助手消息不会进入后续请求历史。
- 开发或测试部署可显式开启对话调试浮动球；正式环境由服务端渲染门禁强制关闭。

## 进度维护规则

1. 按以下阶段推进；开始任务时将状态改为“进行中”，通过验收后再改为“已完成”。状态使用：未开始、进行中、已完成、受阻。
2. 每完成一个任务，立即更新本文对应任务状态和实施记录，写明完成日期、实际行为、代码路径、验证方式与结果、遗留问题。涉及前端的任务也在本文追踪。
3. 部分实现或尚未验证不能标记完成；受阻时记录原因、依赖和下一步。
4. 接口、数据结构、配置或运行方式变化时，同步更新 `docs/backend-architecture.md`、`README.md`；涉及前端时同步更新前端相关文档。规划不能替代当前实现说明。
5. 顺序或范围调整时记录原因及依赖，保留可追溯的变更记录。本文不得包含密钥或真实用户对话内容。

## 阶段零：环境隔离与对话调试工具

状态：已完成（2026-11-23）。已为后续稳定性任务提供可重复的消息与故障场景。

| 编号 | 任务 | 状态 | 验收要求 |
| --- | --- | --- | --- |
| S0-1 | 建立开发、测试、正式环境配置 | 已完成 | 前端和服务端使用 `APP_ENV=development|test|production`；前端另用 `ENABLE_CONVERSATION_DEBUG`。两个仓库均提供不含密钥的 `.env.example`，API 地址和 CORS 仍按部署环境设置。 |
| S0-2 | 增加浮动球和调试面板 | 已完成 | 服务端组件仅在非正式环境且开关为 `true` 时传入启用标志；正式环境即使误设开关也不挂载面板，URL 与浏览器存储无法开启。 |
| S0-3 | 提供本地消息测试操作 | 已完成 | 支持插入用户消息、Markdown 回复、长回复、30 条批量消息、思考占位和停止状态，并支持清空消息及重置场景；操作只影响浏览器内存。 |
| S0-4 | 提供可重复的流式故障注入 | 已完成 | 支持正常、发送前阻止 SSE、部分内容后断流、缺少完成事件和每片段延迟 800ms；正常界面的停止按钮继续用于主动取消。 |
| S0-5 | 验证环境隔离及真实断连 | 已完成 | 开发开关构建、正式环境强制关闭构建、lint 均通过；服务端测试验证关闭 SSE 外层流会主动关闭 Provider 流，修复了上游连接未显式释放的问题。 |

实现建议：前端独立调试模块，通过受控调试适配层驱动对话状态和 ReplyProvider，避免在每个业务组件中散布测试分支。先在浏览器端模拟故障；确需服务端故障注入时，后端必须单独校验环境和开关，正式环境不注册调试接口。测试身份鉴权与数据归属仍属于上线前门槛。

环境标识与 Git 分支各司其职：分支管理代码，环境配置决定运行行为。前后端均创建本地 `test` 分支用于测试集成；不能依靠分支名决定调试入口可见性。生产部署应显式关闭调试能力，环境与部署检查从本阶段建立，并在阶段五复核。

## 阶段一：对话链路稳定性

状态：未开始。阶段零依赖已完成。目标：失败可恢复、重试不重复提问、停止行为可验证。

| 编号 | 任务 | 状态 | 验收要求 |
| --- | --- | --- | --- |
| S1-1 | 生成失败时保留部分回答并标记失败 | 未开始 | 中途失败后保留已有正文和用户问题，显示错误及重试入口。 |
| S1-2 | 增加重试与重新生成 | 未开始 | 对同一问题重新请求，不重复插入用户消息；明确旧回答的替换或保留规则。 |
| S1-3 | 明确停止后的上下文规则 | 未开始 | 明确部分回答是否进入上下文，避免因简单过滤造成不合理的问答排列，并验证后续追问。 |
| S1-4 | 区分错误与恢复操作 | 未开始 | 区分网络不可达、配置错误、鉴权失败、限流、断流等；界面能恢复到可操作状态。 |
| S1-5 | 验证取消和断流清理 | 未开始 | 用户停止、切换或离开页面后，验证后端任务与上游连接得到清理；不承诺模型供应商立即停止计费。 |

主要位置：前端 `src/modules/conversation/hooks/use-conversation.ts`、`services/http-reply-provider.ts`、`components/message-item.tsx`；后端 `app/conversations/service.py`、`app/llm/openai_compatible.py`。

## 阶段二：会话与消息持久化

状态：未开始。依赖：阶段一明确消息状态和重试语义。目标：服务端管理真实历史，刷新后数据仍可读取。

| 编号 | 任务 | 状态 | 验收要求 |
| --- | --- | --- | --- |
| S2-1 | 引入 PostgreSQL、SQLAlchemy、Alembic | 未开始 | 数据库配置、连接生命周期与迁移可复现；文档说明初始化流程。 |
| S2-2 | 建立会话与消息模型 | 未开始 | 会话包含 ID、标题、创建和更新时间；消息包含 ID、会话 ID、角色、正文、状态、顺序和时间；设计后续用户归属扩展。 |
| S2-3 | 增加会话管理与消息查询接口 | 未开始 | 支持创建、列表、消息查询及删除，明确分页、排序、删除规则与不存在资源的响应。 |
| S2-4 | 将流式请求改为服务端加载历史 | 未开始 | 当前问题先保存，后端按会话读取历史再调用模型；明确旧接口迁移或兼容方案，避免重复写入。 |
| S2-5 | 保存生成结果及中断状态 | 未开始 | 完成、失败和停止均有明确落库状态；确定草稿保存频率及进程中断后遗留生成状态的恢复策略。 |

拟议接口（尚未实现，实施时确认契约）：

```text
POST   /api/v1/conversations
GET    /api/v1/conversations
GET    /api/v1/conversations/{id}/messages
POST   /api/v1/conversations/{id}/messages:stream
DELETE /api/v1/conversations/{id}
```

目标流程：提交会话 ID 和当前问题 → 保存用户消息 → 查询历史 → 构造模型上下文 → 流式返回 → 保存回答与最终状态。

建议新增 `app/db/` 连接与迁移设施，在 `app/conversations/` 中增加模型和持久化职责；保持路由、业务逻辑和模型供应商适配分离。
